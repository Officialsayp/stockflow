# Целевые принципы сервисов

## Статус

План. Этот документ фиксирует ограничения для последующих итераций и не подтверждает наличие исполняемых сервисов, API, БД, брокера, метрик или трассировки.

## Границы и владение данными

- сервис соответствует отдельной бизнес-потребности, а не универсальному техническому контейнеру;
- сервис владеет своей предметной областью и логической областью данных;
- данные и функции другого сервиса доступны только через его явные, документированные контракты;
- прямой доступ к чужой БД или таблицам, общий файловый обмен и импорт внутренних пакетов другого сервиса не являются интеграцией.

## Взаимодействие

- внешняя HTTP-граница будет проектироваться как REST через `api-gateway`;
- синхронные внутренние вызовы будут проектироваться через gRPC, асинхронные доменные события — через Kafka;
- для каждого исходящего вызова будут явно заданы таймаут, стратегия обработки ошибок и, если это оправдано, повторы;
- внешний вызов не должен оставаться внутри открытой локальной транзакции;
- все будущие контракты должны быть понятны без неявных соглашений и совместимо развиваться.

## Исполнение и устойчивость

- экземпляры сервисов должны быть независимыми и не хранить межзапросное состояние в памяти;
- постоянное состояние будет храниться во внешнем хранилище, которым владеет соответствующий сервис;
- при недоступности необязательной зависимости сервис должен сохранять максимально возможную полезную функциональность;
- дата и время в будущих контрактах и хранилищах будут передаваться в UTC в формате RFC 3339.

## Наблюдаемость и качество

- для входящих запросов в будущих сервисах будут спроектированы метрики скорости, задержек и ошибок;
- логи будут структурированными и пригодными для корреляции с трассировкой; контекст трассировки будет передаваться в исходящие вызовы;
- с появлением кода будут добавляться быстрые изолированные unit-тесты, интеграционные и сквозные проверки в соответствующие каталоги.

Конкретные форматы логов, имена метрик, health/readiness-эндпоинты, контракты и SLO появятся вместе с первой реализацией и отдельными ADR.
