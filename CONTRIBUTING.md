# Contributing to StockFlow

## Статус проекта

StockFlow находится на bootstrap-этапе. Перед добавлением реализации сверяйте задачу с архитектурными решениями и не добавляйте рабочие компоненты «на будущее» без отдельного решения.

## Границы будущей реализации

Сервис должен владеть своей бизнес-областью и данными. Доступ к данным или функциям другого сервиса проектируется только через явный контракт; прямые запросы к чужому хранилищу, общий файловый обмен и импорт внутренних пакетов другого сервиса не допускаются. Полный набор целевых инвариантов описан в [docs/architecture/principles.md](docs/architecture/principles.md).

## GitHub Flow

- `main` должна оставаться стабильной;
- каждая новая задача выполняется в отдельной ветке;
- до слияния создаётся Pull Request;
- изменения проходят назначенные проверки;
- для слияния используется squash merge;
- после первоначального bootstrap прямые рабочие коммиты в `main` не используются.

Используйте один из префиксов веток:

```text
feature/<short-description>
fix/<short-description>
chore/<short-description>
docs/<short-description>
test/<short-description>
refactor/<short-description>
```

## Инструменты и состояние Git

- Codex и GoLand используйте для создания и изменения файлов;
- GitHub Desktop — для обзора изменений, веток, коммитов, push и pull;
- GitHub в Safari — для Pull Request, review, Issues, Actions и настроек;
- терминал — для проверяемых команд (`go test`, `docker compose`, `git status`, `make`).

Все эти инструменты изменяют один и тот же каталог `.git`. Не выполняйте конфликтующие Git-операции параллельно в нескольких клиентах; после каждой операции обновляйте состояние выбранного клиента.

## Коммиты

Используйте Conventional Commits. Подходящие типы:

```text
feat:
fix:
docs:
test:
refactor:
perf:
build:
ci:
chore:
```

Формулируйте сообщение кратко и в повелительном наклонении. Один Pull Request должен иметь ясную, ограниченную цель.

## Pull Request

В описании PR укажите цель изменения, затронутые границы, проверки и известные ограничения. Не смешивайте в одном PR изменение архитектуры, реализацию функциональности и несвязанные форматирования.

## Безопасность и секреты

Не добавляйте в репозиторий пароли, токены, ключи и локальные `.env`-файлы. Правила сообщения об уязвимостях приведены в [SECURITY.md](SECURITY.md).
