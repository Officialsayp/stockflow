# StockFlow

> **Статус: Initial architecture / Work in progress**

StockFlow — учебная платформа для изучения резервирования товарных остатков и обработки заказов в микросервисной архитектуре на Go. Это не готовый продукт и не демонстрация работающей бизнес-функциональности: на текущем этапе репозиторий содержит только согласованный каркас, документацию и инженерные правила.

## Назначение

Проект служит практической основой для последовательного освоения production-подходов к backend-разработке. Реализация будет добавляться небольшими проверяемыми изменениями; до этого момента здесь нет приложений, API-контрактов, миграций или инфраструктурных сервисов.

## Предполагаемая архитектура

Монорепозиторий объединяет независимые сервисы, будущие публичные и внутренние API-контракты, документацию, тестовые контуры и конфигурацию поставки. Это учебная организация исходных материалов, а не утверждение, что такая же топология репозиториев обязательна для production-команды. Внешние клиенты предполагаются за API Gateway; внутренняя синхронная коммуникация будет проектироваться через gRPC, а доменные события — через Kafka с паттерном transactional outbox.

Планируемые сервисы:

- `api-gateway` — будущая внешняя HTTP-граница и маршрутизация запросов;
- `order-service` — будущая координация заказов и резервирования;
- `inventory-service` — будущий учёт и резервирование товарных остатков;
- `notification-service` — будущая обработка событий и доставка уведомлений.

### Планируемые инварианты границ

- каждый сервис будет соответствовать отдельной бизнес-потребности и владеть своими данными;
- доступ к данным и функциям другого сервиса будет возможен только через явный документированный контракт, а не через прямые запросы к его хранилищу, общий файловый обмен или внутренние пакеты;
- экземпляры сервисов будут независимыми и не будут хранить межзапросное состояние в памяти;
- для внешних вызовов будут явно проектироваться таймауты, обработка ошибок и деградация; внешний вызов не должен выполняться внутри открытой локальной транзакции;
- время в контрактах и хранилищах будет представляться в UTC в формате RFC 3339.

Эти правила описывают целевое направление. Они не означают, что контракты, хранилища, таймауты или наблюдаемость уже реализованы. Детализация находится в [архитектурных принципах](docs/architecture/principles.md).

## Планируемый стек

- Go и модульная монорепозитория;
- PostgreSQL для транзакционных данных;
- REST для публичного API, gRPC и Protocol Buffers для внутреннего API;
- Kafka, Redis и transactional outbox для асинхронных сценариев;
- Docker и Kubernetes для поставки;
- Prometheus, Grafana, OpenTelemetry, Loki и Tempo для наблюдаемости;
- GitHub Actions для автоматизации проверок.

## Инженерные темы

В следующих итерациях проект будет использоваться для практики идемпотентности, конкурентной обработки запросов, согласованности данных, контрактов между сервисами, unit-, integration-, contract- и end-to-end-тестов. Наличие этих каталогов не означает, что соответствующие механизмы уже реализованы.

## Структура

```text
api/             будущие публичные, внутренние и событийные контракты
docs/            архитектурные заметки, ADR, runbooks и диаграммы
services/        границы будущих Go-сервисов
migrations/      будущая зона миграций
deployments/     будущие артефакты поставки
observability/   будущие конфигурации наблюдаемости
tests/           будущие межсервисные тестовые сценарии
tools/           будущие генераторы, скрипты и seed-данные
examples/        будущие примеры вызовов API
```

## Запуск

## Roadmap

1. Уточнить системный дизайн и зафиксировать решения в ADR.
2. Добавить контракты и границы первого сервиса.
3. Ввести минимальный исполняемый сервис и тестовый контур.
4. Подключать хранилища, события и наблюдаемость по одному проверяемому шагу.

## Разработка

Используется GitHub Flow: `main` остаётся стабильной, а каждая последующая задача выполняется в отдельной ветке и попадает в `main` через Pull Request и squash merge. Подробные правила находятся в [CONTRIBUTING.md](CONTRIBUTING.md).

Архитектурные решения собраны в [docs/adr](docs/adr/README.md).

### Инструменты и единое состояние Git

- Codex и GoLand — создание и редактирование файлов;
- GitHub Desktop — просмотр diff, создание веток, коммиты, push и pull;
- Safari/GitHub — Pull Request, review, Issues, Projects, Actions и настройки репозитория;
- терминал — проверяемые команды, например `go test`, `docker compose`, `git status` и `make`.

Все инструменты работают с одним каталогом `.git`. Не запускайте конкурирующие Git-операции одновременно в нескольких интерфейсах: сначала дождитесь завершения операции и обновите состояние в используемом клиенте.

## Тестирование

Каркас содержит будущие зоны для unit-, integration-, contract-, end-to-end-, нагрузочных и chaos-проверок. Реальные тесты и проверка гонок будут добавлены вместе с исполняемым кодом; на bootstrap-этапе исходного кода нет.
